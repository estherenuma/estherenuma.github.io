BUILD 01

AI Lead Qualification & Routing

intake form → database → llm scoring → branch routing

Before

Every enquiry landed in a shared inbox. Someone had to read it, judge how serious it was, log it, and decide who should answer. Hot leads sat unread over weekends, and no two people scored a lead the same way.

After

Intake form writes to a central table, an LLM returns a category, a score out of ten and a one-line rationale, and the result is parsed back and routed — hot straight to Slack with full context, warm to email, the rest into a nurture sequence.

formtableai scoringparsebranchslackemailnurture

Key decision

The form writes to the table before the AI runs, so a model failure never loses a lead. Worst case it sits unscored, not gone.

< 60 sec
from enquiry received to scored and routed. Previously up to a full working day, longer across a weekend.
built in zapier so the team could maintain it in-house · forms · tables · openai · formatter · paths · slack · email
BUILD 02
shipped

Customer-Facing Enquiry Assistant

curated knowledge base → guarded assistant → lead capture

Before

The same handful of questions, answered by a person, over and over, and only during working hours. Anyone browsing at 11pm got nothing and left.

After

A branded assistant answers instantly from a curated knowledge base, under an explicit instruction set — no prices, no commitments, and it declines rather than guesses. Real buying intent gets pushed into the enquiry form.

knowledge baseassistantguardrailsintent detectedform

Key decision

Architected one-way on purpose. The assistant can send people into the lead database but cannot read from it, so no customer data is reachable through a public interface.

24 / 7
answering, qualifying, and capturing intent outside working hours — the window where most of the traffic actually arrives.

03 / About

A builder first. I teach because I build, not the other way round.

approach

My delivery work happens in self-hosted n8n. It handles the things client work actually runs into — real branching logic, custom code where a no-code node runs out, self-hosting when data should not leave a client environment, and no per-task pricing that punishes a system for being used. When a client needs to own and edit the system themselves inside a tool they already pay for, I build it in Zapier or Make instead, and I say so up front.

how I work

I start from the failure modes, not the happy path. What happens when the model returns nonsense, when the API is down, when someone submits the form twice, when the person who owns the process leaves. A system that only works on a good day is not finished. Every build is handed over with a recorded walkthrough and documentation, because a system nobody understands is a system that quietly dies.
